4.1. Vector Data Types and Topology#

4.1.1. Learning objectives#

By the end of this section, you should be able to:

  • distinguish point, line, polygon, and multipart geometries;

  • explain how geometry and attributes form a feature;

  • describe the interior, boundary, and exterior of a geometry;

  • state the conditions that make a point, line, polygon, or multipart geometry valid, and diagnose violations with Shapely;

  • create Shapely geometries and organize them in a GeoSeries or GeoDataFrame;

  • parse geometry values stored as text in a CSV file;

  • inspect a GeoDataFrame before a spatial operation; and

  • describe the four topological relationships (adjacency, connectivity, containment, and coincidence) and the predicate that tests each.

Section goal

A spatial question starts with the feature type it needs. This section builds a small inventory of Calgary point, line, and polygon layers, then checks the validity, topology, and metadata that make those layers usable in later analysis.

4.1.2. The vector data model#

Vector data represents geographic features as discrete coordinate pairs (vertices) connected in defined patterns, together with descriptive attributes. Raster data, by contrast, stores values on a regular grid. Each model answers different questions:

A feature pairs one geometry with a record of attributes. The geometry answers where; the attributes answer what, when, or how much. A library branch is a point plus a name and opening hours; a community district is a polygon plus a code and a name.

4.1.3. Geometric primitives#

Every vector geometry is built from vertices, ordered coordinate tuples, and is classified by its topological dimension: the dimension of the space it occupies, regardless of how many coordinates (x, y, and optionally z) each vertex stores. Table 4.2 lists the three primitives.

Table 4.2 The three geometric primitives.#

Dimension decides what can be measured. A point has neither length nor area, a line has length, and a polygon has both perimeter and area. A ring is a closed LineString whose first and last vertices are identical; Shapely adds the closing vertex if you leave it out. The exterior ring (the shell) bounds the polygon, and interior rings cut holes out of it, such as a pond inside a park.

Each primitive has a multipart form (MultiPoint, MultiLineString, and MultiPolygon) that stores several parts as one feature. A MultiPolygon is not the same as several unrelated rows: a multipart feature is counted once, dissolved once, and carries one attribute record. That distinction matters when counting parks, calculating areas, or assigning a point to a district. A GeometryCollection can mix types in one feature, but many operations and file formats do not support it, so treat one as a cue to clean the data.

Shapely [Gillies et al., 2026] geometries can be created directly, which is useful for testing predicates and for understanding what a file parser produces:

4.1.4. Interior, boundary, and exterior#

Both validity and topology rest on one idea: every geometry divides the plane into three disjoint parts [University of L'Aquila and Clementini, 2025]. The interior is the geometry itself without its edge, the boundary is the edge, and the exterior is everything else. Table 4.3 shows how the parts depend on the type.

Table 4.3 Interior and boundary by geometry type.#

The boundary of a geometry has one dimension fewer than the geometry itself: a polygon’s boundary is a line, and a line’s boundary is a set of points. This is why a point on a park’s edge is not inside the park in the topological sense, a distinction that returns in the validity rules and in the predicates below.

4.1.5. What makes a geometry valid?#

A geometry is valid when it obeys the OGC Simple Features rules [Herring, 2011] that Shapely (through GEOS [GEOS: Geometry Engine - Open Source, 2024]), PostGIS, and most GIS software implement. The rules differ by type because each type can go wrong in its own way. Validity is a property of a single geometry, checked without reference to any other feature.

Software will usually store an invalid geometry without complaint. The problem appears later as a wrong area, an unreliable predicate, or an exception during overlay. Two terms are often confused:

  • valid: the geometry conforms to the rules for its type; and

  • simple: the geometry does not cross or touch itself. A line that crosses itself is valid but not simple.

4.1.5.1. Points#

A Point is valid when its coordinates are finite numbers. A single vertex cannot intersect itself, so there is no geometric rule beyond that; NaN or infinite coordinates, usually left by a failed parse, are what make a point invalid. An empty point is valid, and it differs from a missing value (None), which has no geometry at all. A MultiPoint is valid when every member is; duplicate members make it non-simple but not invalid.

Validity does not mean correctness. A point with latitude and longitude swapped is a perfectly valid point, in the wrong place. Range and bounds checks catch that error, not is_valid.

4.1.5.2. LineStrings#

A LineString is valid when it has at least two distinct vertices, so it has non-zero length, and its coordinates are finite. Repeated consecutive vertices are tolerated.

A line that crosses itself is valid but not simple, which is correct for a looping trail and usually a digitising error for a street or rail centreline, where a crossing without a shared vertex means a missing intersection node. A closed line has identical first and last vertices, and a closed and simple line is a ring (is_ring). Rings are the building blocks of polygons.

4.1.5.3. Polygons#

A Polygon has the most rules, because a ring can fail in several ways. A polygon is valid when:

  1. every ring is closed and has at least four coordinates (three distinct vertices plus the repeated first);

  2. every ring is simple: it does not cross or touch itself, which excludes bow-ties, spikes, and zero-width slivers;

  3. every hole lies inside the shell;

  4. rings touch one another only at isolated points, never along an edge, and holes do not overlap each other; and

  5. the interior is connected, so no pair of touching rings cuts the polygon into separate pieces.

Ring direction is not part of the rules. GeoJSON [Butler et al., 2016] recommends a counter-clockwise shell and clockwise holes, and readers must accept either. A bow-tie shows why rule 2 matters: its ring winds one way around one lobe and the opposite way around the other, so the signed-area formula cancels and the reported area collapses.

4.1.5.4. Multipart geometries#

A MultiLineString is valid when each member line is valid; members may cross or touch. A MultiPolygon is valid when each member polygon is valid and the member interiors do not overlap. Parts may touch at a point, but not along an edge: two parts that share an edge should be one polygon, so software requires the merge.

4.1.6. GeoSeries and GeoDataFrames#

A GeoSeries [Jordahl et al., 2020] is a pandas Series whose values are geometries; it exposes geometry-aware properties such as geom_type, bounds, and total_bounds. A GeoDataFrame adds attribute columns and designates one geometry column as active.

Assigning a CRS with set_crs (or the crs= argument) only labels coordinates that already use that CRS; it never transforms them. The Calgary sources store longitude and latitude, so EPSG:4326 is the correct label for the layers built below.

4.1.8. Load the Calgary layers#

The Calgary layers [Open Calgary: The City of Calgary Open Data Portal, 2026] arrive in three encodings. The library CSV stores points as (latitude, longitude) text, the LRT and community CSV files store geometry as well-known text (WKT), and the parks GeoJSON carries geometry directly. Keep the raw columns and make every conversion explicit so a parsing choice can be audited later. The coordinate range check in the parser guards against the most common CSV mistake: swapping latitude and longitude.

Show code cell source

Hide code cell source

 
from pathlib import Path

import pandas as pd

# Jupyter Book and an interactive notebook can use different working directories.
DATA_DIR = Path('../data') if Path('../data').exists() else Path('data')


def location_to_point(value):
    '''Convert Calgary '(latitude, longitude)' text to a Point.'''
    parts = [float(part.strip()) for part in value.strip('() ').split(',')]
    if len(parts) != 2:
        raise ValueError(f'Expected latitude and longitude, got: {value!r}')
    latitude, longitude = parts
    if not 49 <= latitude <= 53 or not -117 <= longitude <= -111:
        raise ValueError(f'Unexpected Calgary coordinate order or range: {value!r}')
    return Point(longitude, latitude)


libraries_raw = pd.read_csv(DATA_DIR / 'Calgary_Public_Library_Locations_and_Hours_20240620.csv')
libraries = gpd.GeoDataFrame(
    libraries_raw,
    geometry=libraries_raw['Location'].map(location_to_point),
    crs='EPSG:4326',
).reset_index(names='branch_id')

stations_raw = pd.read_csv(DATA_DIR / 'Transit_LRT_Stations_20240901.csv')
stations = gpd.GeoDataFrame(
    stations_raw,
    geometry=gpd.GeoSeries.from_wkt(stations_raw['the_geom']),
    crs='EPSG:4326',
).reset_index(names='station_id')

tracks_raw = pd.read_csv(DATA_DIR / 'Tracks_-_LRT_20240622.csv')
tracks = gpd.GeoDataFrame(
    tracks_raw,
    geometry=gpd.GeoSeries.from_wkt(tracks_raw['the_geom']),
    crs='EPSG:4326',
).reset_index(names='track_id')

4.1.9. Inspect geometry types and CRS#

The geometry column is not just another text column: GeoPandas uses it to expose geometry-aware properties and operations. The CSV-based layers are assigned WGS 84 because their source coordinates are longitude and latitude, and the parks layer inherits its CRS from the GeoJSON file. WGS 84 is useful for mapping, but its units are degrees rather than metres.

The first inspection of any layer should answer four questions:

  • What is the CRS?

  • How many rows are there?

  • Which geometry types are present?

  • Are any geometries missing or invalid? (see Table 4.4)

The one invalid district, row 309, fails at a single vertex (a ring self-intersection near −114.111, 50.921): one localized fault among 313 districts, not a pattern across the layer. It is still a row in the layer, so an area sum or overlay that includes it needs a repair first.

4.1.11. Topology is about relationships#

Geometry describes where a feature is: coordinates, lengths, and areas that change when you reproject or edit a vertex. Topology describes how features relate to one another, and those relationships survive a change of CRS. Four relationship types cover the questions asked most often:

  • Adjacency: which features share a boundary (two neighbouring districts);

  • Connectivity: which features join end to end (track segments that form a route);

  • Containment: which features lie inside others (a library within a district); and

  • Coincidence: which features occupy the same location (a station that sits on a track).

A point’s coordinates alone do not say whether it belongs to a park or district. That meaning comes from a predicate such as within. Likewise, a collection of nearby line features is not automatically a connected transport network; endpoints and gaps must be checked.

Each predicate is a statement about how the interior, boundary, and exterior of geometry A meet those of geometry B. touches requires that the interiors do not meet while the boundaries do, so polygons that share an edge touch, and polygons that share area overlap. intersects is the broadest test: it is True for any contact and is the exact opposite of disjoint.

Two edge cases matter in practice. A point on a polygon’s edge is not within it, because it lies on the boundary, not the interior, but covers accepts it. And touches is also True for a T-junction, where one line ends on the middle of another, so strict end-to-end connectivity needs the endpoints compared directly.

The complete answer is the DE-9IM matrix [Egenhofer and Franzosa, 1991, University of L'Aquila and Clementini, 2025] that relate returns: nine characters, one for each pairing of A’s interior, boundary, and exterior with B’s, recording the dimension of the overlap (F for none, 0 for points, 1 for lines, 2 for areas). The named predicates are readable patterns over that string. A toy example makes the edge cases visible.

4.1.12. Why topology matters#

Predicates such as within, touches, and intersects turn coordinates into answers: they drive spatial joins, network construction, and quality control. They also carry a performance lesson. Comparing every feature against every other feature is quadratic in the number of features, so GeoPandas predicates and joins use a spatial index to test only candidates whose bounding boxes overlap. Checking total_bounds and geometry validity first keeps those operations fast and correct.

Validity concerns one geometry at a time. Topology rules concern the layer as a whole, and every geometry in a layer can be valid while the layer still breaks them, as in Table 4.7.

4.1.13. Summary#

Points, lines, polygons, and multipart geometries encode different spatial meanings, and each divides space into an interior, a boundary, and an exterior. A geometry is valid only if it meets the rules for its type: finite coordinates for points, at least two distinct vertices for lines, and closed, simple, properly nested rings with connected interiors for polygons. Validity is about one geometry; topology is about how features relate, and layer-level rules such as no overlaps or gaps are checked separately. The Calgary sources also show how a geometry type can hide inside a file format: a CSV may contain points or lines as text or WKT, while GeoJSON exposes its geometry directly. Inspect geometry types, CRS, bounds, missing values, and validity before choosing an operation. Continue with S02 for measurements and derived geometries.
