3.5. OpenStreetMap Data#

3.5.1. Learning Objectives#

By the end of this section, you should be able to:

  • Describe OpenStreetMap’s crowd-sourced, tag-based data model (nodes, ways, relations) and how its elements become GIS geometries.

  • Query OpenStreetMap data with the Overpass API and load extracts with osmnx and pyrosm.

  • Choose between pyrosm and osmnx based on extract size and workflow.

  • Explain why OpenStreetMap data requires a coordinate reference system check before analysis, and choose a suitable projected CRS.

  • Assess the completeness of tags in an extract and credit OpenStreetMap correctly.

Section Goal

Unlike the file formats covered so far, OpenStreetMap (OSM) is not delivered as a single downloadable dataset with one schema — it is a live, global, crowd-sourced database queried or extracted on demand. This section introduces its data model and shows two Python tools, pyrosm and osmnx, for turning OSM data into GeoDataFrames.

3.5.2. The OpenStreetMap Data Model#

OpenStreetMap [OpenStreetMap Contributors, 2026] represents the world with three primitive element types:

  • Nodes: single points with latitude/longitude (e.g., a fire hydrant, a tree).

  • Ways: ordered lists of nodes forming a line or polygon (e.g., a road, a building outline).

  • Relations: ordered collections of nodes, ways, and other relations, used to model structures a way alone cannot express (e.g., a bus route, a multi-polygon lake with islands).

Every element carries tags — free-form key=value pairs — instead of a fixed schema. A single node might be tagged amenity=restaurant, cuisine=italian, and name=Luigi's, while a way might be tagged highway=residential and maxspeed=30. This flexibility is OSM’s greatest strength and its main data-quality challenge: tagging conventions are community-maintained and not always applied consistently [Haklay, 2010].

3.5.3. Querying with the Overpass API#

The Overpass API [OpenStreetMap Contributors, 2026] lets you query OSM’s database directly using a purpose-built query language, returning only the elements matching your filter rather than an entire regional extract.

A query has three parts: an optional output format and timeout ([out:json][timeout:60];), a set of filters that select elements, and an out statement that decides what to return. The query below asks for hospitals in Calgary, and it improves on a simple node-only query in three ways:

  • area["name"="Calgary"]["boundary"="administrative"] restricts the area to an administrative boundary, so another place that happens to be named Calgary does not match.

  • nwr searches nodes, ways, and relations. Hospitals are often mapped as building outlines (ways), and a node-only query would miss them.

  • out center; returns a single center point for each way or relation, so every result has coordinates. (out body; returns tags and node references but no geometry for ways.)

Table 3.30 Overpass Output Modes#

Statement

Returns

out body;

Tags, and for ways the node references, but no coordinates for ways

out center;

Tags plus one center point for each way and relation

out geom;

Tags plus the full coordinates of every way and relation

out count;

Only the number of matching elements

Overpass is well suited to targeted queries (e.g., “all hospitals in Calgary”) but becomes slow or memory-intensive for large regional extracts — for those, a downloaded .osm.pbf extract read locally is faster. It is also a shared public service: it enforces rate limits and timeouts, expects a meaningful User-Agent, and may reject requests when busy. Follow the same discipline as for any API (narrow queries, cache the response, retry with backoff).

Overpass returns JSON with an elements list. The cell below parses a sample response with that structure into a GeoDataFrame; the values are invented for illustration and are not real hospitals. Nodes carry lat and lon; ways and relations carry a center. The same function works on a live response.

[out:json][timeout:60];
area["name"="Calgary"]["boundary"="administrative"]->.searchArea;

"""

def overpass_to_gdf(elements):
    """Turn Overpass JSON elements into a GeoDataFrame, using each element's point or center."""
    rows = []
    for element in elements:
        position = element if element["type"] == "node" else element.get("center")
        if position is None:                       # e.g., a way returned with 'out body;' has no coordinates
            continue
        rows.append({"osm_type": element["type"], "osm_id": element["id"], **element.get("tags", {}),
                     "geometry": gpd.points_from_xy([position["lon"]], [position["lat"]])[0]})
    return gpd.GeoDataFrame(rows, crs="EPSG:4326")

3.5.4.1. Bulk Extraction with pyrosm#

pyrosm reads a local PBF file and returns GeoDataFrames for the layers you ask for: buildings, points of interest, the street network, and more. It can fetch a city extract from BBBike by name and caches it, so the download happens only once. The next cell uses the Calgary, Alberta extract, restricts it to a bounding box around downtown so the layers stay small, and reads buildings, restaurant and café points of interest, and the driving network from the same file. The three requests parse the file locally, which is why several layers from one file are cheap.

Hide code cell source

 
from pathlib import Path
from pyrosm import OSM, get_data

# pyrosm downloads a named BBBike city extract once and reuses the cached file
fp = get_data("Calgary", directory="data/osm")

# Read only a downtown bounding box [west, south, east, north] to keep the layers small
downtown_bbox = [-114.095, 51.035, -114.045, 51.060]

# Set complete_relations=True to handle relations extending beyond the bounding box
osm = OSM(fp, bounding_box=downtown_bbox, complete_relations=True)

buildings = osm.get_buildings()
pois = osm.get_pois(custom_filter={"amenity": ["restaurant", "cafe"]})
nodes, edges = osm.get_network(network_type="driving", nodes=True)

print(
    f"Extract: {Path(fp).name}, {Path(fp).stat().st_size / 1e6:.2f} MB (read"
    " within a downtown bounding box)"
)

)
print(f"pois      : {len(pois):>5}  {pois.geom_type.value_counts().to_dict()}")
print(f"network   : {len(edges):>5} street segments joining {len(nodes)} nodes")
print(f"CRS       : {buildings.crs.to_string()}")

3.5.4.2. Street Networks with osmnx#

osmnx is built for street networks. It does not return a plain table: it returns a graph (a networkx multi-digraph) in which intersections are nodes and street segments are edges, ready for routing and network statistics. It then converts the graph to GeoDataFrames when you want to map or filter it.

In normal use, osmnx fetches the data itself:

graph = ox.graph_from_place("Crater Lake National Park, Oregon, USA", network_type="drive")

That call geocodes the place name and queries Overpass, so it needs a network connection and uses the shared services politely. osmnx can also build a graph from a local OSM XML file, which is what the next cell does, using the tiny file from the start of this section. It converts the graph to node and edge tables, finds a shortest path along the street grid, and draws the route.

Show code cell source

Hide code cell source

 
import osmnx as ox

graph = ox.graph_from_xml(mini_path)
graph_nodes, graph_edges = ox.graph_to_gdfs(graph)
print(f"Graph: {graph.number_of_nodes()} nodes (intersections and dead ends), {graph.number_of_edges()} directed edges")
print("Edge columns:", graph_edges.columns.tolist())

origin, destination = list(graph.nodes)[0], list(graph.nodes)[-1]
route = ox.shortest_path(graph, origin, destination, weight="length")
route_length = sum(graph.edges[u, v, 0]["length"] for u, v in zip(route[:-1], route[1:]))
print(f"Shortest path from node {origin} to node {destination}: nodes {route}, {route_length:.0f} m")

3.5.5. Coordinate Reference System Considerations#

OpenStreetMap data is always distributed in WGS84 (EPSG:4326), geographic coordinates in degrees. This is fine for storage and web mapping, but degree-based coordinates make area, length, and distance calculations meaningless without reprojection first.

Choosing the projected CRS needs care. The usual choice for a local study area is a UTM zone, but UTM [Snyder, 1987] divides the world into 6-degree-wide zones, and a zone is accurate only near its own central meridian. The earlier version of this section used EPSG:32612 (UTM zone 12N, covering 114°W to 108°W) for Crater Lake, Oregon, which lies near 122°W, in zone 10 (EPSG:32610). The result is still in meters, so nothing signals the mistake. GeoPandas can pick the zone for you with estimate_utm_crs(), from the data’s own extent.

The cell below measures the same Calgary buildings in four ways: in the zone GeoPandas chooses, in the two neighboring zones, and in a zone that is far from the study area (zone 17). It also shows what happens if you ask for the area in degrees.

3.5.6. How Complete Are the Tags?#

Because tags are free-form, an OSM extract is only as complete as its contributors made it. Before treating a layer as authoritative, measure how many features actually carry the tags you need. The cell below computes the share of downtown Calgary buildings with each of six useful tags, and maps which buildings have a house number. The shares apply to this small extract only; completeness differs from place to place [Barrington-Leigh and Millard-Ball, 2017], which is exactly why you must measure it for your own study area.

Show code cell source

Hide code cell source

 
tag_columns = ["name", "addr:housenumber", "addr:street", "building:levels", "height", "start_date"]
# reindex keeps a tag that never occurs in this extract as a 0% bar instead of raising a KeyError
completeness = buildings.reindex(columns=tag_columns).notna().mean().mul(100).sort_values()

print(completeness.round(1).sort_values(ascending=False).to_string())

addr:street         53.9
building:levels     49.4
name                20.2
height               4.4
start_date           0.8

In Fig. 3.22, only the address tags are about half complete (54% of buildings have a house number), building:levels is at 49%, name at 20%, height at 4%, and start_date at under 1%. The map shows that the gaps are patchy rather than uniform, with whole blocks lacking numbers beside blocks that have them. Treat these shares as a property of this extract, not of OpenStreetMap in general.

A map like the right-hand panel is a quick way to see whether missing tags are scattered at random or concentrated in certain areas, which affects what any analysis built on them can claim. Treat the absence of a tag as “not recorded”, not as “does not exist”, as discussed in the Geospatial ETL, Open Data, and Licensing section.

3.5.7. Crediting OpenStreetMap#

OpenStreetMap data is published under the Open Database License (ODbL) [Open Data Commons, 2026]. In practice, this means two obligations: you must credit the source, and derived databases that you publish must be shared under the same license. The expected credit line is “© OpenStreetMap contributors” [OpenStreetMap Contributors, 2026], and it belongs on the map itself, as in the figure above, not only in a notebook or a report’s fine print. Check the license terms of any other layer you combine with OSM data before you publish the result.

3.5.8. When to Use OpenStreetMap Data#

  • Rapid prototyping without licensing negotiation (OSM is under the Open Database License).

  • Street network and routing analysis.

  • Filling gaps where authoritative government data is unavailable or costly.

  • Applications where community-maintained currency (frequent contributor edits) outweighs the need for official certification.

Caveats: coverage and tagging completeness vary significantly by region; always validate attribute completeness (for example, missing addr:housenumber tags) before treating an extract as authoritative.

For a hands-on comparison of Overpass queries, pyrosm, and osmnx against the same study area, see the labs.

Meaning

A free-form key=value pair describing an element.

3.5.11. Summary#

OpenStreetMap trades a fixed schema for flexible, community-maintained tags organized into nodes, ways, and relations, queried live through Overpass or extracted in bulk as .osm.pbf files. pyrosm suits repeated bulk extraction from a local file, while osmnx suits routable network graphs and one-off queries; either way, reproject out of WGS84 into a suitable projected CRS before measuring area or distance, measure how complete the tags are before relying on them, and credit OpenStreetMap contributors in what you publish.
