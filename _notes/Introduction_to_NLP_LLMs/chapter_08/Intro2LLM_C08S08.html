8.8. Lightweight Local Models for Agentic AI: 7B Models, GPU Offload, and Grammar-Constrained Decoding#

8.8.1. Learning objectives#

By the end of this section, you should be able to:

  • Explain why quantized 7B instruction-tuned models are a practical “lightweight” choice for local agentic AI, and how they compare to 1–3B CPU-only models.

  • Load Mistral-7B-Instruct and Qwen2.5-7B-Instruct in GGUF format with llama-cpp-python, using GPU offload with a graceful fallback.

  • Build a complete tool-calling agent loop in plain Python, with no agent framework.

  • Use grammar-constrained decoding (GBNF) to make malformed tool calls structurally impossible, and state precisely what it does and does not fix.

  • Apply the hybrid strategy: the LLM plans and routes, deterministic Python tools do the precise work.

  • Measure speed (tokens/second), accuracy, and failure modes, and attribute failures to the right cause (format, tool choice, or reasoning).

8.8.2. Why lightweight local models for agentic AI?#

Agentic systems call the model many times per task (once per reasoning step), so latency, cost, and privacy matter more than in a single-shot chatbot. Running a model locally is attractive when:

  • Privacy is critical: data must not leave local infrastructure.

  • Throughput and cost matter: an agent loop may issue 3–10 generations per question, and per-token API costs multiply.

  • Teaching and prototyping: students need models that run on hardware they control.

  • Edge deployment: laptops and workstations with a single consumer GPU.

Earlier versions of this section focused on 1–3B models (TinyLlama-1.1B, Phi-2-2.7B) running on a CPU. That approach works for simple one-tool tasks, but it hits two walls: speed (a few tokens per second on CPU) and format reliability (small models frequently narrate instead of acting, echo placeholders, or invent tool names). Two engineering changes address these walls directly, and they are the subject of this section:

  1. GPU offload of a 4-bit quantized 7B model. Quantization shrinks a 7B model to roughly 4.5 GB, small enough for a mid-range consumer GPU, and offloading all layers to the GPU raises throughput from single-digit tokens/second (CPU) to tens of tokens/second or more, depending on hardware.

  2. Grammar-constrained decoding. Instead of asking the model to emit a parseable format and regex-parsing whatever comes back, we constrain the sampler so that only format-valid tokens can be produced.

Two practical points about the 7B models:

  • Both are instruction-tuned, not base/completion models, so we call them through create_chat_completion with the correct chat_format. Using the wrong template is one of the most common causes of garbled output, so we pick the right one up front rather than debugging it later.

  • Q4_K_M is a 4-bit “k-quant” scheme that keeps quality close to the full-precision model at about a quarter of the memory footprint.

VRAM note

Holding both 7B models in memory at once needs roughly 10 GB of VRAM. If your GPU has less, free the first model (del model; gc.collect()) before loading the second, or run the models one at a time.

8.8.4. What grammar constraints fix, and what they do not#

A GBNF grammar (GGML BNF) is a formal description of the strings the model is allowed to produce. At every sampling step, llama.cpp masks out any token that would take the output outside the grammar. The model is not “trying” to follow the format; it cannot leave it.

Fixed (structural errors):

  • Narrated text mistaken for a tool call (for example, “I will use the TOOL format to…”).

  • Placeholder text echoed verbatim (for example, <your answer>).

  • Invented tool names: the TOOL: field can only be filled with a name in the registry.

Not fixed (semantic errors). The model can still reason incorrectly inside a valid structure:

  • Choosing the wrong (but valid) tool for the task.

  • Getting arithmetic or logic backwards.

  • Misreading what a tool’s arguments mean.

  • Failing to stop once the question has already been answered.

Moving from 1–3B to 7B reduces the frequency of these semantic errors; it does not eliminate them. Keeping this division clear (format correctness is a decoding problem; reasoning correctness is a capability problem) is the main conceptual takeaway of this section.

8.8.5. The agent loop#

The agent in this section is a short loop. There is no framework: just a model, a tool registry, a grammar, and a parser.

8.8.7. Loading the models#

Two design decisions are worth noticing in the loader:

  1. chat_format matches the fine-tuning template. Mistral-Instruct uses [INST] ... [/INST]; Qwen2.5-Instruct uses ChatML (<|im_start|> / <|im_end|>). Both are built into llama-cpp-python.

  2. Graceful degradation. n_gpu_layers=-1 offloads every layer. If that fails (typically out of VRAM), we retry with partial offload and finally CPU-only, instead of crashing. Partial offload is a useful middle ground: layers on the GPU run fast, the rest run on the CPU.

Hide code cell source

 
def load_with_gpu_fallback(model_path, **kwargs):
    """Try full GPU offload, then partial, then CPU-only, rather than hard-crashing
    on a card with less VRAM than expected."""
    for n_gpu_layers, label in [(-1, "full GPU offload"), (20, "partial GPU offload"), (0, "CPU only")]:
        try:
            llm = Llama(model_path=model_path, n_gpu_layers=n_gpu_layers, **kwargs)
            print(f"Loaded with: {label} (n_gpu_layers={n_gpu_layers})")
            return llm
        except Exception as e:
            print(f"  {label} failed ({e}); trying next option...")
    raise RuntimeError("Could not load model under any GPU configuration.")

8.8.8. Speed benchmark#

We measure generation throughput in tokens per second. Two details matter for a fair measurement:

  • Use the model’s own token count (usage.completion_tokens), not a whitespace word count. Word counts under-count tokens (a typical English word is more than one token), which makes reported speeds look slower than they are.

  • Run a warm-up generation first; the first call includes one-time setup costs (kernel initialization, cache allocation).

The measured time includes prompt processing, so short prompts and short outputs slightly understate steady-state decode speed. That is fine for comparing configurations, as long as you hold the prompt fixed.

Show code cell source

Hide code cell source

 
def measure_speed(llm, prompt="Explain what a tool-calling agent is in three sentences.",
                  max_tokens=128, runs=3):
    """Return average completion tokens/second over several runs (after one warm-up)."""
    messages = [{"role": "user", "content": prompt}]
    llm.create_chat_completion(messages=messages, max_tokens=8, temperature=0.0)   # warm-up
    rates = []
    for _ in range(runs):
        t0 = time.time()
        out = llm.create_chat_completion(messages=messages, max_tokens=max_tokens, temperature=0.0)
        dt = time.time() - t0
        rates.append(out["usage"]["completion_tokens"] / dt)
    return sum(rates) / len(rates)

8.8.9.1. Five practical tools#

The tools are intentionally small, but they include the defensive patterns that matter once an LLM is the caller:

  • Input sanitization. Models decorate arguments with labels, units, or restated answers (for example 650 * 30 (total cost) = 19500). The calculator strips parenthetical labels, drops everything after =, and whitelists characters before calling eval.

  • Informative errors. Every failure returns a message that tells the model how to fix its call, so the agent can recover on the next step.

  • Skip-and-report. The GPA tool ignores malformed entries and reports what it skipped, rather than failing the whole call.

# ── Tool 1: Calculator ───────────────────────────────────────────────
def calculator(expression: str) -> str:
    """Evaluate arithmetic. Input: Python math expression. Returns: result."""
    # Strip parenthetical labels that contain letters, e.g. "(cost per credit hour)".
    # Real numeric grouping parentheses are unaffected.
    expression = re.sub(r'\([^)]*[a-zA-Z][^)]*\)', '', expression)
    # Models sometimes write "expr = result ... narration": keep only the part before '='.
    expression = expression.split('=')[0]
    # Whitelist: digits, whitespace, + - * / . ( ) %
    clean = re.sub(r'[^\d\s\+\-\*\/\.\(\)\%]', '', expression)
    if not clean.strip():
        return "Calculator error: no expression given. Provide something like '30 * 650'."
    try:
        return f"{eval(clean, {'__builtins__': {}, 'math': math}, {})}"
    except Exception as e:
        return f"Error: {e}"


# ── Tool 2: Date and time ────────────────────────────────────────────
def get_date() -> str:
    """Return today's date and time. No input needed."""
    return datetime.datetime.now().strftime("Today is %A, %B %d, %Y. Time: %H:%M.")


# ── Tool 3: Unit converter ───────────────────────────────────────────
def unit_convert(value: str, from_unit: str, to_unit: str) -> str:
    """Convert between km/miles, kg/lbs, celsius/fahrenheit, liters/gallons, meters/feet."""
    try:
        v = float(value)
        key = f"{from_unit.lower()}_{to_unit.lower()}"
        conversions = {
            "km_miles": v * 0.621371,      "miles_km": v * 1.60934,
            "kg_lbs": v * 2.20462,         "lbs_kg": v * 0.453592,
            "celsius_fahrenheit": v * 9 / 5 + 32,
            "fahrenheit_celsius": (v - 32) * 5 / 9,
            "liters_gallons": v * 0.264172, "gallons_liters": v * 3.78541,
            "meters_feet": v * 3.28084,    "feet_meters": v * 0.3048,
        }
        if key in conversions:
            return f"{v} {from_unit} = {round(conversions[key], 4)} {to_unit}"
        return f"Unsupported conversion: {from_unit} to {to_unit}"
    except Exception as e:
        return f"Conversion error: {e}"


# ── Tool 4: GPA calculator ───────────────────────────────────────────
def gpa_calculator(grades_and_credits: str) -> str:
    """Input 'A:3,B+:4,A-:3,C:2' (grade:credit_hours pairs, comma or newline separated)."""
    grade_points = {
        'A': 4.0, 'A-': 3.7, 'B+': 3.3, 'B': 3.0, 'B-': 2.7,
        'C+': 2.3, 'C': 2.0, 'C-': 1.7, 'D+': 1.3, 'D': 1.0, 'D-': 0.7, 'F': 0.0,
    }
    try:
        total_points = total_credits = 0.0
        breakdown, skipped = [], []
        for entry in re.split(r'[,\n]', grades_and_credits.strip()):
            entry = entry.strip()
            if ':' not in entry:
                continue
            grade, credits = entry.split(':', 1)
            grade = grade.strip().upper()
            if grade not in grade_points:
                skipped.append(entry)
                continue
            try:
                credits = float(credits.strip())
            except ValueError:
                skipped.append(entry)
                continue
            pts = grade_points[grade] * credits
            total_points += pts
            total_credits += credits
            breakdown.append(f"{grade}({credits}cr)={pts:.1f}pts")
        if total_credits == 0:
            return "No valid grades found. Use 'A:3,B+:4' format (letter grade : credit hours)."
        note = f" | Ignored: {', '.join(skipped)}" if skipped else ""
        return (f"GPA: {total_points / total_credits:.2f} | Total credits: {total_credits} | "
                f"Total points: {total_points:.1f} | Breakdown: {', '.join(breakdown)}{note}")
    except Exception as e:
        return f"GPA error: {e}"

def knowledge_lookup(query: str) -> str:
    """Look up a topic. Tries exact match, then substring match, then shared-word match."""
    q = query.lower().strip()
    if not q:
        return "No topic given. Provide a keyword, e.g. 'nlp', 'rag', 'msds program'."
    if q in KNOWLEDGE_BASE:
        return KNOWLEDGE_BASE[q]
    for key, value in KNOWLEDGE_BASE.items():
        if q in key or key in q:
            return value
    q_words = set(q.split())
    for key, value in KNOWLEDGE_BASE.items():
        if q_words & set(key.split()):
            return value
    return f"'{query}' not found in local knowledge base. Available topics: {', '.join(KNOWLEDGE_BASE)}"

8.8.10. Tool registry and grammar#

TOOL_REGISTRY is the single source of truth for tool names. Both the system prompt’s tool list and the GBNF grammar are generated from it, so they cannot drift out of sync. Adding a tool means adding one registry entry; the prompt and the grammar update themselves.

The grammar forces every generation into exactly this shape:

THOUGHT: <free text>
TOOL: <one registered tool name, or "answer">
INPUT: <free text, may be empty>

The TOOL: line is the important one. The model does not sample free text there; it chooses among the finite set of names the grammar allows. Everything else stays free text, because we want the model to keep its flexibility where flexibility is useful (the reasoning and the tool input).

Reading the GBNF rules:

Table 8.10 GBNF Grammar Rule Breakdown#

Rule

Meaning

root

The whole output: three labelled lines in a fixed order

toolname

An alternation of the literal tool names (plus answer)

line

Any run of characters except a newline ([^\n]*)

ws

Zero or more spaces after a label

Implementation detail

The newline in the grammar must reach llama.cpp as the two-character escape \n, which GBNF interprets as a newline. That is why the template below is a raw f-string (rf"""..."""). In an ordinary f-string, Python would turn \n into a real newline character inside the quoted literal and the grammar would fail to compile.

8.8.11. Prompt design for local agents#

Grammar handles format; the prompt still has to communicate the task. The principles from earlier versions of this section still hold, and the 7B models make them cheaper to satisfy:

  1. Keep the system prompt short and unambiguous. One role sentence, the tool list, the format, one example. Long prompts packed with instructions are followed unevenly, especially by smaller models.

  2. Generate the tool list from the registry, as shown below, so the prompt always matches the grammar.

  3. Include one format example. An example pattern is followed more reliably than an abstract format description. With a grammar the example no longer has to teach the format; it mainly shows how to choose a tool and write its input.

  4. Anchor every continuation to the original question. After a tool returns, small and mid-size models are prone to treating the new RESULT as a fresh task, or to continuing past a correct answer. The continuation prompt below repeats the original question and asks one explicit yes/no decision: does this result already answer it?

Item 4 is a prompt-level fix for a semantic failure, which is exactly the kind of failure a grammar cannot address.

8.8.12. Parsing and tool execution#

With the grammar active, the parser never meets narrated text or invented tool names. We still keep a defensive parser for two reasons: it is the fallback path when grammar support is unavailable, and it is the baseline for the ablation experiment later in this section.

One subtle rule: the parser takes the last TOOL: match, not the first. In ungrammared output, a model may narrate the format before acting (“I will use the TOOL: format…”), and the first match would be the narration.

execute_tool also handles a messy-input case for unit_convert, the only tool with three arguments: it accepts the preferred value, from, to form, and falls back to labelled lines when the model writes them that way.

def parse_agent_output(text: str) -> dict:
    """Parse THOUGHT:/TOOL:/INPUT: lines. Uses the LAST 'TOOL:' occurrence as a safety net
    for the no-grammar path (a model may narrate the format before acting)."""
    result = {"tool": None, "input": None, "raw": text, "parse_success": False}
    tool_matches = list(re.finditer(r'TOOL:\s*(\w+)', text, re.IGNORECASE))
    if tool_matches:
        last = tool_matches[-1]
        result["tool"] = last.group(1).strip().lower()
        result["parse_success"] = True
        remainder = text[last.end():]
        m = re.search(r'INPUT:\s*(.+?)(?:\nRESULT:|THOUGHT:|TOOL:|$)', remainder,
                      re.IGNORECASE | re.DOTALL)
        if m:
            result["input"] = m.group(1).strip()
    return result


def execute_tool(tool_name: str, tool_input: str) -> str:
    tool_name = tool_name.lower().strip()
    tool_input = (tool_input or "").strip()

    if tool_name not in TOOL_REGISTRY:
        return f"Unknown tool '{tool_name}'. Available: {', '.join(TOOL_REGISTRY)}, answer"

    if tool_name == "unit_convert":
        parts = [p.strip() for p in tool_input.split(',') if p.strip()]
        if len(parts) == 3:
            return unit_convert(*parts)
        # Fallback: labelled lines, e.g. "19500\nFROM_UNIT: dollars\nTO_UNIT: miles"
        v  = re.search(r'[-+]?\d*\.?\d+', tool_input)
        fu = re.search(r'FROM_UNIT:\s*(\S+)', tool_input, re.IGNORECASE)
        tu = re.search(r'TO_UNIT:\s*(\S+)',   tool_input, re.IGNORECASE)
        if v and fu and tu:
            return unit_convert(v.group(0), fu.group(1), tu.group(1))
        return "Format: value, from_unit, to_unit (e.g., '100, km, miles')"

    try:
        return TOOL_REGISTRY[tool_name]["func"](tool_input)
    except Exception as e:
        return f"Tool error: {e}"

8.8.13. The agent class#

The agent holds the conversation as a chat message list and loops until the model emits TOOL: answer or the step limit is reached. Three design points:

  • A fresh LlamaGrammar per call. This avoids relying on any implicit grammar state being reset between generations.

  • Stop sequences ("\nRESULT:", "\nOriginal question:") stop the model from hallucinating the tool’s output or the next user turn.

  • Instrumentation. The agent records steps, parse failures, token counts, and elapsed time for every run. We use these statistics later to diagnose failures rather than guess at them. Token counts come from usage.completion_tokens, not word counts.

Hide code cell source

 
class LightweightAgent:
    def __init__(self, llm, name: str, max_steps: int = 6,
                 max_tokens_per_step: int = 256, use_grammar: bool = True):
        self.llm = llm
        self.name = name
        self.max_steps = max_steps
        self.max_tokens_per_step = max_tokens_per_step
        self.use_grammar = use_grammar and GRAMMAR_AVAILABLE
        self.tool_calls = []
        self.stats = {}

    def _generate(self, messages):
        kwargs = dict(
            messages=messages,
            max_tokens=self.max_tokens_per_step,
            temperature=0.1,
            stop=["\nRESULT:", "\nOriginal question:"],
        )
        if self.use_grammar:
            kwargs["grammar"] = LlamaGrammar.from_string(TOOL_GRAMMAR_TEXT)
        response = self.llm.create_chat_completion(**kwargs)
        text = response["choices"][0]["message"]["content"]
        n_tokens = response.get("usage", {}).get("completion_tokens", len(text.split()))
        return text, n_tokens

    def run(self, question: str, verbose: bool = True) -> str:
        self.tool_calls = []
        self.stats = {"steps": 0, "parse_failures": 0, "tokens": 0,
                      "time_s": 0.0, "finished": False}
        messages = [
            {"role": "system", "content": AGENT_SYSTEM_PROMPT},
            {"role": "user",   "content": question},
        ]
        if verbose:
            print("━" * 57)
            print(f"[{self.name}] QUESTION: {question}")
            print("━" * 57)

        t0 = time.time()
        for step in range(1, self.max_steps + 1):
            generated, n_tokens = self._generate(messages)
            self.stats["steps"] = step
            self.stats["tokens"] += n_tokens
            if verbose:
                print(f"\n  [Step {step}]\n  Model: {generated.strip()}")

            parsed = parse_agent_output(generated)

            if not parsed["parse_success"]:
                self.stats["parse_failures"] += 1
                if verbose:
                    print("  ⚠ Could not parse tool call — asking model to retry.")
                messages.append({"role": "assistant", "content": generated})
                messages.append({"role": "user", "content": RETRY_PROMPT})
                continue

            tool_name, tool_input = parsed["tool"], parsed["input"] or ""

            if tool_name == "answer":
                self.stats["time_s"] = time.time() - t0
                self.stats["finished"] = True
                if verbose:
                    s = self.stats
                    print(f"\n  ✓ FINAL ANSWER: {tool_input}")
                    print(f"  Steps: {s['steps']} | Tokens: {s['tokens']} | "
                          f"Time: {s['time_s']:.1f}s | Speed: {s['tokens'] / s['time_s']:.1f} tok/s")
                return tool_input

            result = execute_tool(tool_name, tool_input)
            self.tool_calls.append({"tool": tool_name, "input": tool_input, "result": result})
            if verbose:
                print(f"  → Calling: {tool_name}({tool_input})")
                print(f"  ← Result: {result[:100]}")

            messages.append({"role": "assistant", "content": f"{generated}\nRESULT: {result}"})
            messages.append({"role": "user",
                             "content": CONTINUE_PROMPT.format(question=question, result=result)})

        self.stats["time_s"] = time.time() - t0
        return ("I reached my step limit. Here is what I found: "
                + (self.tool_calls[-1]["result"] if self.tool_calls else "insufficient information."))

Instead of eyeballing six transcripts, we turn the questions into a small test suite with expected answers and score every run automatically. Each test has a set of acceptable substrings; an answer is counted correct if it contains one of them after normalization (lower-casing, removing $, commas, and spaces).

def normalize(s: str) -> str:
    return re.sub(r'[,$\s]', '', s.lower())

def is_correct(answer: str, expect: list) -> bool:
    a = normalize(answer)
    return any(normalize(e) in a for e in expect)

def classify(row: dict) -> str:
    """Attribute each run to a cause. Order matters: format problems first."""
    if row["parse_failures"] > 0:
        return "format (parse failure)"
    if not row["finished"]:
        return "loop (step limit)"
    if not row["correct"]:
        return "reasoning (wrong answer)"
    return "ok"

def run_suite(agents, suite=TEST_SUITE):
    rows = []
    for test in suite:
        for agent in agents:
            answer = agent.run(test["question"], verbose=False)
            row = dict(test=test["label"], model=agent.name, grammar=agent.use_grammar,
                       answer=answer, correct=is_correct(answer, test["expect"]),
                       tools=[c["tool"] for c in agent.tool_calls], **agent.stats)
            row["cause"] = classify(row)
            rows.append(row)
    return rows

def print_results(rows):

8.8.16. Ablation: what does the grammar actually buy?#

An ablation removes one component to measure its contribution. Here we rerun the same suite with use_grammar=False, so the models generate freely and the regex parser has to cope. Everything else is identical: same models, prompts, tools, and tests.

What to look for:

  • Parse failures should rise without the grammar. This is the effect the grammar is designed to remove.

  • Accuracy may change much less than parse failures do. If it does, that confirms the central claim of this section: the grammar fixes format, while remaining errors are reasoning errors.

  • Instruction-tuned 7B models are already fairly good at following a three-line format, so the gap can be smaller than it was for TinyLlama and Phi-2. Report what you measure, not what you expected.

8.8.17. Reading the results#

Use the Cause column to attribute each failure. The three categories call for three different remedies:

Table 8.12 Failure Mode Analysis and Remedies#

Cause

What happened

Right fix

format (parse failure)

Output did not match the expected structure

Grammar-constrained decoding; stricter retry prompt

loop (step limit)

The model kept calling tools after the answer was available

Question-anchored continuation prompt; lower step limit; stop conditions

reasoning (wrong answer)

Valid structure, wrong tool, wrong arguments, or wrong interpretation

Better tool descriptions, fewer or clearer tools, a larger model, or a verification step

If grammar-constrained runs show zero parse failures, the constraint is working. If you still see ⚠ Could not parse tool call, check the printed GRAMMAR_AVAILABLE and use_grammar values first: grammar compilation may have silently fallen back.

A frequent pattern in these experiments is that the multi-step and conversion questions are where models differ most, because they require choosing between plausible tools or chaining two operations. Single-tool questions are usually solved by both models.

The key capability gap remains multi-step reasoning reliability. Grammar-constrained decoding makes the form of each step trustworthy; it does not make the content of each step correct. For agents whose mistakes are costly, combine the grammar with deterministic tools, result verification, and a human-in-the-loop check.

8.8.19. Key takeaways#

  • A 4-bit 7B model is “lightweight” in the sense that matters for deployment: it fits on one consumer GPU and runs at interactive speed.

  • GPU offload addresses speed; grammar-constrained decoding addresses format reliability. They solve different problems.

  • Generate the prompt’s tool list and the grammar from one registry, so they cannot disagree.

  • Let the LLM reason and route; let Python tools compute.

  • Instrument your agent and classify failures by cause. Treating “the agent failed” as one problem leads to the wrong fix.

8.8.20. Exercises and discussion#

  1. Grammar ablation, extended. Using run_suite, repeat the with/without-grammar comparison five times per condition and report the mean and range of accuracy and parse failures. How much of the variation is format versus reasoning? Is the benefit of the grammar larger for the 7B models or for TinyLlama/Phi-2 (load them via llama-cpp-python on CPU and reuse the same suite)?

  2. GPU offload sweep. Reload one model with n_gpu_layers in {0, 10, 20, -1} and call measure_speed for each. Plot tokens/second against the number of offloaded layers. Is the relationship linear? What does the curve suggest about the best configuration for a GPU with half the VRAM?

  3. Extend the toolset and the grammar. Add a sixth tool (for example, percent_change or date_diff) by adding a single entry to TOOL_REGISTRY. Verify that the system prompt and TOOL_GRAMMAR_TEXT both update without any other code changes. Then add two test questions that need the new tool and measure whether tool misselection increases as the tool count grows from 5 to 6.

  4. Constrain the arguments, too. The current grammar constrains only the tool name; INPUT: is free text. Write a stricter rule for unit_convert so that its input must look like <number>, <unit>, <unit> with units drawn from the supported set. What is the trade-off between a stricter grammar and flexibility? Which failures from the results table would this remove?

  5. Prompt sensitivity. Compare three variants on the full suite: (a) the current system prompt, (b) the system prompt without the example, (c) the system prompt with the CONTINUE_PROMPT replaced by a plain “Continue.” Which change affects loop failures the most? Which affects format failures the most (run with and without the grammar)?

  6. Task routing design. Design a router that sends each incoming question to the cheapest adequate model: a small model for single-tool questions and a 7B model for multi-step questions. Implement the classifier as a grammar-constrained prompt (output restricted to simple or complex) and measure routing accuracy on 20 labelled questions. What does a misrouting cost: a wrong answer, or only extra latency?
