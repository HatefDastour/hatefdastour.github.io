8.3.3. Building Tools for Agents#

8.3.3.1. Learning objectives#

By the end of this section, you should be able to:

  • Explain the four requirements that every agent tool must satisfy.

  • Write a Python function that meets the tool requirements: clear name, precise description, typed parameters, and error handling.

  • Implement a tool registry that maps tool names to their callable functions and descriptions.

  • Explain how the agent uses tool descriptions to make tool selection decisions.

  • Design tools for common agent use cases: information retrieval, computation, data access, and I/O.

8.3.3.2. What Is a Tool?#

A tool is a Python function that the agent can call to interact with the world — the mechanism by which language models can be equipped to invoke external APIs and compensate for capabilities such as precise arithmetic that they otherwise lack [Schick et al., 2023]. Tools give the agent capabilities that the LLM backbone alone cannot provide:

  • Real-time information — web search, weather APIs, stock prices

  • Mathematical precision — a calculator that computes without rounding errors

  • Database access — structured queries on local or remote data

  • File I/O — reading documents, writing outputs

  • Code execution — running Python, SQL, or shell commands

  • External service integration — sending emails, posting to APIs

Without tools, an agent is limited to what the model’s weights encode. With tools, the agent becomes a general-purpose actor that can interact with any system.

The Four Tool Requirements

Every tool needs four components:

  1. Clear name The LLM refers to the tool by name in its Action line. Names must be unique, descriptive, and short. Good: “web_search”, “python_calculator”, “get_weather” Bad: “tool1”, “function”, “do_stuff”

  2. Precise description The LLM reads descriptions to decide which tool to call. Descriptions should state:

    • What the tool does

    • What type of input it expects

    • What type of output it returns

    • When to use it (and when NOT to use it)

  3. Typed parameters Well-typed parameters help the LLM format input correctly. The LLM learns from the type annotation what format to use.

  4. Error handling A tool that crashes with an exception will terminate the agent loop. Tools must catch errors and return descriptive error strings instead.

import math
import json
import datetime
import requests
from typing import Optional

# Tool 1: Web search
def web_search(query: str) -> str:
    """
    Search the web for current information.
    Use for: facts, news, prices, recent events.
    Input: a concise search query (string).
    Output: a text summary of search results.
    """
    try:
        # Note: the `duckduckgo_search` package was renamed to `ddgs` on PyPI
        # (install with `pip install ddgs`). The old import path still works for now
        # but prints a deprecation warning and will eventually stop working.
        from ddgs import DDGS
        with DDGS() as ddgs:
            results = list(ddgs.text(query, max_results=3))
            if not results:
                return "No results found for that query."
            summaries = [f"{r['title']}: {r['body']}" for r in results]
            return "\n".join(summaries[:3])
    except Exception as e:
        return f"Search error: {str(e)}"


# Tool 2: Python calculator
def python_calculator(expression: str) -> str:
    """
    Evaluate a mathematical expression.
    Use for: arithmetic, unit conversions, percentage calculations.
    Input: a Python arithmetic expression (e.g., '1999 * 0.85', 'math.sqrt(144)').
    Output: the computed result as a string.
    Do NOT use for: non-numeric operations.
    """
    import re
    # Strip parenthetical labels/units that contain letters, e.g. "(cost per credit hour)" --
    # these are annotations, not math grouping. Real numeric grouping parens are unaffected.
    expression = re.sub(r'\([^)]*[a-zA-Z][^)]*\)', '', expression)
    # Models sometimes write "expr = result ... more narration" in one line -- take only the
    # part before the first '=', since that's the actual expression, not its restated answer.
    expression = expression.split('=')[0]
    # Whitelist safe characters before eval. We keep word characters (not just digits) so
    # legitimate calls like 'math.sqrt(144)' still work -- the real safety net is the
    # sandboxed safe_globals below (no builtins, only `math` exposed), not this whitelist.
    clean = re.sub(r'[^\w\s\+\-\*\/\.\(\)\%]', '', expression)
    if not clean.strip():
        return "Calculation error: no numeric expression given."
    try:
        # Restrict to safe mathematical operations
        safe_globals = {"__builtins__": {}, "math": math}
        result = eval(clean, safe_globals)
        return str(round(float(result), 6))
    except ZeroDivisionError:
        return "Error: division by zero"
    except Exception as e:
        return f"Calculation error: {str(e)}"


# Tool 3: Get current date and time
def get_current_datetime(format: str = "%Y-%m-%d %H:%M UTC") -> str:
    """
    Return the current date and time.
    Use for: questions about today's date, current time, days of the week.
    Input: optional datetime format string (default: YYYY-MM-DD HH:MM UTC).
    Output: the current datetime as a formatted string.
    """
    try:
        # datetime.utcnow() is deprecated as of Python 3.12; use a timezone-aware call instead.
        return datetime.datetime.now(datetime.timezone.utc).strftime(format)
    except Exception as e:
        return f"Datetime error: {str(e)}"


# Tool 4: Unit converter
def unit_converter(value: float, from_unit: str, to_unit: str) -> str:
    """
    Convert a value between common units.
    Use for: temperature, distance, weight conversions.
    Input: value (number), from_unit (e.g., 'celsius'), to_unit (e.g., 'fahrenheit').
    Output: the converted value with units.
    Supported conversions: celsius\u2194fahrenheit, km\u2194miles, kg\u2194pounds.
    """
    conversions = {
        ("celsius", "fahrenheit"): lambda x: x * 9/5 + 32,
        ("fahrenheit", "celsius"): lambda x: (x - 32) * 5/9,
        ("km", "miles"): lambda x: x * 0.621371,
        ("miles", "km"): lambda x: x / 0.621371,
        ("kg", "pounds"): lambda x: x * 2.20462,
        ("pounds", "kg"): lambda x: x / 2.20462,
    }
    key = (from_unit.lower(), to_unit.lower())
    if key not in conversions:
        return f"Unsupported conversion: {from_unit} to {to_unit}"
    try:
        result = conversions[key](float(value))
        return f"{value} {from_unit} = {round(result, 4)} {to_unit}"
    except Exception as e:
        return f"Conversion error: {str(e)}"

8.3.3.4. The Tool Registry#

A tool registry is a central catalog that maps tool names to their callable functions and descriptions. The agent uses the registry to enumerate available tools and build its system prompt:

class ToolRegistry:
    def __init__(self):
        self.tools: dict[str, dict] = {}

    def register(self, func, name: str = None, description: str = None):
        """Register a function as a tool."""
        tool_name = name or func.__name__
        tool_desc = description or func.__doc__ or "No description provided."
        self.tools[tool_name] = {
            "function": func,
            "description": tool_desc.strip(),
        }

    def call(self, name: str, input_str: str) -> str:
        """Call a registered tool by name with a string input."""
        if name not in self.tools:
            available = ", ".join(self.tools.keys())
            return f"Unknown tool '{name}'. Available tools: {available}"
        try:
            return self.tools[name]["function"](input_str)
        except Exception as e:
            return f"Tool error: {str(e)}"

    def describe_all(self) -> str:
        """Return a formatted description of all available tools."""
        lines = []
        for name, info in self.tools.items():
            lines.append(f"- {name}: {info['description']}")
        return "\n".join(lines)


# Initialize and populate the registry
registry = ToolRegistry()
registry.register(web_search,          name="search")
registry.register(python_calculator,   name="calculator")
registry.register(get_current_datetime, name="datetime")
registry.register(unit_converter,      name="convert_units")

# Print the tool menu that will be injected into the agent's system prompt
print(registry.describe_all())

- search: Search the web for current information.
    Use for: facts, news, prices, recent events.
    Input: a concise search query (string).
    Output: a text summary of search results.
- calculator: Evaluate a mathematical expression.
    Use for: arithmetic, unit conversions, percentage calculations.
    Input: a Python arithmetic expression (e.g., '1999 * 0.85', 'math.sqrt(144)').
    Output: the computed result as a string.
    Do NOT use for: non-numeric operations.
- datetime: Return the current date and time.
    Use for: questions about today's date, current time, days of the week.
    Input: optional datetime format string (default: YYYY-MM-DD HH:MM UTC).
    Output: the current datetime as a formatted string.
- convert_units: Convert a value between common units.
    Use for: temperature, distance, weight conversions.
    Input: value (number), from_unit (e.g., 'celsius'), to_unit (e.g., 'fahrenheit').
    Output: the converted value with units.
    Supported conversions: celsius↔fahrenheit, km↔miles, kg↔pounds.

The describe_all() output is injected into the agent’s system prompt so the model knows what tools exist and when to use each one.

8.3.3.5. Tool Design Principles#

Table 8.4 Tool Design Principles#

Principle

Explanation

Single responsibility

Each tool does one thing; composition handles complex tasks

Defensive error handling

Never raise exceptions from a tool; always return error strings

Idempotent where possible

Calling a tool twice with the same input should give the same result

Input flexibility

Accept natural language inputs where possible; parse internally

Output clarity

Return human-readable strings, not raw data structures

8.3.3.6. Exercises and discussion#

  1. Tool description quality Take the python_calculator tool description and rewrite it to be maximally vague (single line, no examples, no “when to use”). Run an agent with the vague description on five prompts that require calculation. Compare tool selection accuracy (correct tool chosen?) with the original detailed description.

  2. Custom tool implementation Implement a word_counter tool that counts the number of words, sentences, and paragraphs in a text input. Write the docstring to meet all four tool requirements. Test the tool both directly and within an agent on prompts like “How many words are in the following paragraph?”

  3. Error handling test Deliberately pass invalid inputs to each tool in the library: a non-numeric string to python_calculator, an unsupported unit pair to unit_converter, a malformed expression to web_search. Verify that each tool returns an informative error string rather than raising an exception. Modify any tool that does raise an exception.
