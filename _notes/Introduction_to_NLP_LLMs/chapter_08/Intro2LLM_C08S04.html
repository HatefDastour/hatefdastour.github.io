8.4. Agent Memory Systems#

8.4.1. Learning objectives#

By the end of this section, you should be able to:

  • Distinguish the three types of agent memory: short-term working memory, episodic conversation memory, and long-term semantic memory.

  • Explain how working memory is implemented using the prompt context window.

  • Implement episodic memory as an append-only conversation log.

  • Implement a basic long-term memory store with semantic recall using keyword or embedding-based retrieval.

  • Explain the trade-offs between the three memory types in terms of capacity, recall precision, and implementation complexity.

8.4.2. Why Agents Need Memory#

An agent with no memory treats every reasoning step in isolation. This creates three classes of failure:

  1. Within-task repetition — the agent calls the same tool twice because it forgot the first result.

  2. Within-session forgetting — the agent cannot reference information the user provided earlier in the conversation.

  3. Across-session loss — every new session starts from zero, even for returning users with established preferences.

Each failure class requires a different memory strategy.

The working/episodic/long-term decomposition below is consistent with recent taxonomies of memory in LLM-based agents [Wang et al., 2024], and the retrieval-based design used for long-term memory follows the memory-stream approach popularized by generative agent architectures [Park et al., 2023].

8.4.3. Three Types of Agent Memory#

8.4.4. Working Memory: the Context Window#

Working memory is the simplest memory type — it is just the prompt. Every thought, action, and observation the agent generates becomes part of the growing context that conditions subsequent reasoning:

Hide code cell source

 
class WorkingMemory:
    def __init__(self):
        self.trace: list[dict] = []

    def add(self, role: str, content: str):
        """Add a step to the working memory trace."""
        self.trace.append({"role": role, "content": content})

    def to_prompt(self) -> str:
        """Format the trace for injection into the agent prompt."""
        lines = []
        for entry in self.trace:
            lines.append(f"{entry['role'].capitalize()}: {entry['content']}")
        return "\n".join(lines)

    def clear(self):
        """Clear working memory at task completion."""
        self.trace.clear()

    @property
    def token_estimate(self) -> int:
        """Rough token count for context window management."""
        return len(self.to_prompt()) // 4  # ~4 chars per token

Working memory grows with every step in the agent loop. For long tasks (10+ steps), it may approach the context window limit. A common mitigation is to summarize the working memory trace every N steps, replacing the growing trace with a compact summary.

8.4.5. Episodic Memory: Conversation Log#

Episodic memory records the history of exchanges between the user and agent within a session:

Show code cell source

Hide code cell source

 
class EpisodicMemory:
    def __init__(self, max_turns: int = 20):
        self.history: list[dict] = []
        self.max_turns = max_turns

    def add_exchange(self, user_input: str, agent_response: str):
        """Record a complete user-agent exchange."""
        self.history.append({
            "user": user_input,
            "agent": agent_response,
        })
        # Trim to max_turns to prevent unbounded growth
        if len(self.history) > self.max_turns:
            self.history = self.history[-self.max_turns:]

    def to_context(self, n_recent: int = 5) -> str:
        """Return the last n_recent exchanges formatted for injection."""
        recent = self.history[-n_recent:]
        lines = []
        for exchange in recent:
            lines.append(f"User: {exchange['user']}")
            lines.append(f"Agent: {exchange['agent']}")
        return "\n".join(lines)

    def recall_matching(self, keyword: str) -> list[dict]:
        """Return exchanges containing a keyword."""
        return [e for e in self.history if keyword.lower() in
                (e["user"] + e["agent"]).lower()]

Episodic memory is typically injected at the start of the agent’s context window as a “conversation history” section, before the current task. The n_recent parameter limits how much history is injected — a balance between recall and context window consumption.

8.4.6. Long-Term Semantic Memory#

Long-term memory persists facts across sessions. A simple implementation uses keyword-based lookup over a list of stored facts:

Hide code cell source

 
class SemanticMemory:
    def __init__(self):
        self.facts: list[dict] = []

    def store(self, content: str, metadata: dict = None):
        """Store a fact with optional metadata."""
        self.facts.append({
            "content": content,
            "metadata": metadata or {},
        })

    def recall_relevant(self, query: str, top_k: int = 3) -> list[str]:
        """
        Retrieve facts relevant to the query.
        This implementation uses simple keyword overlap.
        Production systems would use vector embeddings for semantic search.
        """
        query_words = set(query.lower().split())

        scored_facts = []
        for fact in self.facts:
            fact_words = set(fact["content"].lower().split())
            overlap = len(query_words & fact_words)
            if overlap > 0:
                scored_facts.append((overlap, fact["content"]))

        scored_facts.sort(reverse=True)
        return [content for _, content in scored_facts[:top_k]]

    def recall_context(self, query: str) -> str:
        """Return recalled facts formatted for prompt injection."""
        facts = self.recall_relevant(query)
        if not facts:
            return "No relevant memories found."
        return "Relevant memories:\n" + "\n".join(f"- {f}" for f in facts)

For production systems, the keyword-overlap retrieval should be replaced with vector similarity search using sentence embeddings (FAISS [Johnson et al., 2019], ChromaDB, or Pinecone). This enables semantic retrieval — finding relevant facts even when the query doesn’t share exact words with the stored fact.

8.4.7. Integrating Memory into an Agent#

A complete agent memory system combines all three types:

Show code cell source

Hide code cell source

 
class AgentMemory:
    def __init__(self):
        self.working = WorkingMemory()
        self.episodic = EpisodicMemory(max_turns=20)
        self.semantic = SemanticMemory()

    def build_context(self, current_goal: str) -> str:
        """Build the full memory context for injection into the agent prompt."""
        parts = []

        # Long-term facts relevant to the current goal
        relevant = self.semantic.recall_context(current_goal)
        if "No relevant" not in relevant:
            parts.append(f"[Background knowledge]\n{relevant}")

        # Recent conversation history
        recent = self.episodic.to_context(n_recent=3)
        if recent:
            parts.append(f"[Recent conversation]\n{recent}")

        # Current task trace
        trace = self.working.to_prompt()
        if trace:
            parts.append(f"[Current task trace]\n{trace}")

        return "\n\n".join(parts)

8.4.8. Exercises and discussion#

  1. Memory type selection For each of the following agent queries, identify which memory type (working, episodic, or semantic) is primarily needed: (a) “What did I ask you about yesterday?”, (b) “Continue the analysis from the previous step”, (c) “My preferred output format is always JSON — remember this for all future responses”, (d) “What is the result of the calculation I asked you to do two steps ago?”

  2. Context window budget An agent has a 2,048-token context window. The system prompt uses 200 tokens. The current task goal is 50 tokens. Estimate how many tokens each memory type consumes (5 recent episodic exchanges at 60 tokens each, 3 semantic facts at 30 tokens each, 4 working memory steps at 80 tokens each). Does everything fit? If not, what would you cut first?

  3. Keyword vs. semantic retrieval Populate a SemanticMemory with 10 facts about a topic. Submit 5 queries — some that use the exact words from stored facts and some that are semantically related but use different vocabulary. Compare the recall results from keyword matching vs. what you would expect from embedding-based similarity search. For which queries does keyword matching fail?
