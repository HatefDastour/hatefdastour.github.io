7.6. Building and Evaluating RAG Chains#

7.6.1. Learning objectives#

By the end of this section, you should be able to:

  • Compose a retriever and an LLM into a grounded RAG chain using the pipe operator.

  • Explain the mechanism by which prompt-level grounding instructions reduce hallucination.

  • Distinguish what ROUGE and BERTScore each measure, and interpret cases where they disagree.

  • Explain when LLM-as-judge evaluation is preferable to automated overlap metrics, and its limitations.

7.6.2. Integrating Retrieval into Prompts#

A RAG prompt has two variable components: context — the chunks retrieved for the query — and question — the user’s query itself. The model is explicitly instructed to answer only from the supplied context; this instruction, combined with the presence of grounded text, is the key mechanism that suppresses hallucination in a RAG pipeline.

Show code cell source

Hide code cell source

 
from langchain_core.prompts import PromptTemplate

rag_template = """<|user|>
Use only the context below to answer the question.
If the answer is not in the context, say "I don't know."

Context:
{context}

Question: {question}<|end|>
<|assistant|>"""

rag_prompt = PromptTemplate(
    template=rag_template, input_variables=["context", "question"]
)

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

def answer(query, retriever, k=2):
    docs = retriever.similarity_search(query, k=k)
    context = format_docs(docs)
    return (rag_prompt | llm).invoke({"context": context, "question": query})

print(answer("What is ChromaDB used for?", chroma_db))

 ChromaDB is used for storing and retrieving embeddings efficiently.

7.6.3. RAG vs. Non-Grounded Generation#

Running the same question through a plain LLM chain and through the RAG chain above makes the effect of grounding concrete: the ungrounded model tends to produce longer, more generic, and occasionally fabricated detail, while the grounded model’s answer stays confined to what the retrieved context actually supports. This gap widens for domain-specific or recent information that is unlikely to be well represented in the model’s training data.

Show code cell source

Hide code cell source

 
standard_prompt = PromptTemplate(
    template="<|user|>\nAnswer the following question: {question}<|end|>\n<|assistant|>",
    input_variables=["question"],
)
standard_chain = standard_prompt | llm

query = "What is FAISS and who developed it?"
print("Ungrounded:", standard_chain.invoke({"question": query}))
print("Grounded:  ", answer(query, chroma_db))

Ungrounded:  FAISS (Facebook Awareness of Interesting Searches) is a library developed by Facebook's Artificial Intelligence Research (FAIR) team to efficiently index and search through large sets of vectors. It primarily focuses on solving nearest neighbor search problems, which are crucial in many applications such as recommendation systems, natural language processing tasks like semantic search or document similarity detection, and object recognition where embeddings need rapid retrieval from a database.

FAISS supports various efficient data structures for indexing high-dimensional vectors (up to 3072 dimensions) and employs both tree-based methods and approximate nearest neighbor search algorithms to offer fast and scalable solutions in handling large datasets. The library is written in C++ but also provides Python bindings, making it accessible across multiple programming languages.

FAISS was initially developed by the FAIR team at Facebook (now Meta) as a research project to explore efficient methods for vector search tasks that are challenging due to their scale and dimensionality. Over time, FAISS has been open-sourced under an Apache License v2.0, allowing it to be adopted and utilized by various organizations and projects beyond Facebook/Meta.

The development of FAISS showcases the ongoing efforts in the machine learning community to address challenges related to search efficiency in high-dimensional spaces, particularly within applications that require real-time responses with large volumes of data.
Grounded:    FAISS is a library developed by Meta for efficient similarity search at scale.

7.6.4. Evaluating RAG Quality: Automated Metrics#

RAG pipeline quality is typically assessed along three dimensions.

What It Measures

from rouge_score import rouge_scorer
from bert_score import score as bert_score

reference = "FAISS is a library developed by Meta for efficient similarity search at scale."
generated = answer(query, chroma_db)

scorer = rouge_scorer.RougeScorer(["rouge1", "rougeL"], use_stemmer=True)
rouge = scorer.score(reference, generated)

P, R, F1 = bert_score([generated], [reference], lang="en", verbose=False)

print(f"ROUGE-1 F1: {rouge['rouge1'].fmeasure:.3f} | ROUGE-L F1: {rouge['rougeL'].fmeasure:.3f}")
print(f"BERTScore F1: {F1.mean():.3f}")

ROUGE-1 F1: 1.000 | ROUGE-L F1: 1.000
BERTScore F1: 1.000

ROUGE measures lexical overlap and is blind to paraphrase; BERTScore measures embedding-level similarity and is more robust to reworded but semantically equivalent answers. A high BERTScore paired with a low ROUGE score is a signal that the answer is semantically correct but worded differently from the reference — not necessarily an error.

7.6.5. LLM-as-Judge Evaluation#

Overlap metrics require a reference answer and can miss nuanced quality differences. An alternative is to prompt a (typically stronger) LLM to score the answer directly against the retrieved context, mimicking how a human expert would grade it. A common rubric scores three criteria on a 1–5 scale:

  • Faithfulness — is the answer grounded in the context?

  • Completeness — does it fully answer the question?

  • Clarity — is it clear and well-structured?

Show code cell source

Hide code cell source

 
judge_template = """<|user|>
You are an expert evaluator. Score the following answer on three criteria,
each from 1 (poor) to 5 (excellent): faithfulness, completeness, clarity.

Context provided to the model:
{context}

Question: {question}

Answer to evaluate:
{answer}

Provide a score and one-sentence justification for each criterion.<|end|>
<|assistant|>"""

judge_prompt = PromptTemplate(
    template=judge_template, input_variables=["context", "question", "answer"]
)
judge_chain = judge_prompt | llm

docs = chroma_db.similarity_search(query, k=2)
evaluation = judge_chain.invoke({
    "context": format_docs(docs), "question": query, "answer": generated,
})
print(evaluation)

 Faithfulness: 5 - The answer directly and accurately addresses the question about who developed FAISS.

Completeness: 1 - While the developer is correctly identified, the response does not mention embeddings or their relationship with FAISS's functionality.

Clarity: 4 - The information provided is clear but lacks detail on how FAISS operates and its relevance to embeddings.

LLM-as-judge is particularly useful when reference answers are unavailable, when answers are too complex for simple overlap metrics, or when nuanced evaluation across multiple dimensions is needed.

Note

LLM-as-judge results can vary between runs. For production evaluation, average scores across multiple runs for reliability.

7.6.6. Exercises and discussion#

  1. Faithfulness failure case Construct a query whose retrieved context does not actually contain the answer. Does the grounded chain correctly respond “I don’t know,” or does it hallucinate despite the grounding instruction? What does this imply about the limits of prompt-level grounding alone?

  2. Metric disagreement Find or construct a generated answer with a low ROUGE score but a high BERTScore. Explain in your own words why the two metrics disagree, and which one better reflects answer quality in that case.

  3. Designing a judge rubric The LLM-as-judge template above scores faithfulness, completeness, and clarity. Propose a fourth criterion relevant to a RAG application you are familiar with, and write the rubric line you would add to the judge prompt.
