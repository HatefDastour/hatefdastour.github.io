7.7. Advanced RAG Patterns#

7.7.1. Learning objectives#

By the end of this section, you should be able to:

  • Explain how hybrid search combines dense and sparse retrieval, and why this helps on domain-specific terminology.

  • Describe a query-routing scheme for multi-document RAG and its limitations.

  • Explain how agentic RAG differs from a fixed retrieve-then-generate pipeline.

7.7.2. Hybrid Search#

Dense vector search retrieves by semantic similarity but can miss exact keyword matches — for example, a rare acronym or product code that the embedding model has not learned to represent distinctly. Hybrid search combines dense retrieval with a sparse keyword method such as BM25, then merges the two ranked lists.

from langchain_community.retrievers import BM25Retriever
from langchain_classic.retrievers import EnsembleRetriever

bm25_retriever = BM25Retriever.from_documents(text_chunks)
bm25_retriever.k = 2

faiss_retriever = faiss_db.as_retriever(search_kwargs={"k": 2})

ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, faiss_retriever],
    weights=[0.5, 0.5],
)

results = ensemble_retriever.invoke("What is ChromaDB?")
for doc in results:
    print(doc.page_content)

LangChain is a framework for developing applications powered by language models.
It provides tools for chaining prompts, managing memory, and integrating external tools.
FAISS is a library developed by Meta for efficient similarity search at scale.
Embeddings are numerical representations of text that capture semantic meaning.
RAG stands for Retrieval-Augmented Generation. It grounds LLM outputs in external knowledge.
ChromaDB is a vector store optimized for storing and retrieving embeddings efficiently.

The weights parameter controls how much each retriever’s ranking contributes to the merged result; tuning it is corpus-dependent and generally requires a small retrieval evaluation set.

7.7.3. Multi-Document RAG#

As a knowledge base grows to cover multiple distinct topics, indexing everything into a single vector store can dilute retrieval precision. Multi-document RAG maintains separate vector stores per topic and routes each query to the appropriate store before retrieval.

Hide code cell source

 
midpoint = len(text_chunks) // 2
store_a = FAISS.from_documents(text_chunks[:midpoint], embeddings)
store_b = FAISS.from_documents(text_chunks[midpoint:], embeddings)

def route_query(query):
    if "chroma" in query.lower():
        return store_a.similarity_search(query, k=2)
    return store_b.similarity_search(query, k=2)

for doc in route_query("What is ChromaDB?"):
    print(doc.page_content)

The keyword-matching router above is illustrative only; production systems typically route with an embedding-based topic classifier or a lightweight LLM call, since keyword rules do not generalize beyond the terms they were written for.

7.7.4. Agentic RAG#

The pipelines covered so far retrieve unconditionally on every query. Agentic RAG instead exposes retrieval as a tool the model can choose to invoke — deciding when retrieval is needed, reformulating the query if the first retrieval attempt is unproductive, and issuing multiple retrieval calls within a single reasoning trace.

Hide code cell source

 
from langchain_core.tools import tool

@tool
def retrieve_context(query: str) -> str:
    """Retrieve relevant context from the knowledge base for a given query."""
    docs = chroma_db.similarity_search(query, k=2)
    return format_docs(docs)

print("Tool registered:", retrieve_context.name)

Tool registered: retrieve_context

Agentic RAG is more capable on multi-hop questions that require several retrieval rounds, at the cost of higher latency and less predictable behavior than a fixed pipeline.

7.7.5. Conclusions#

Retrieval-Augmented Generation is one of the most impactful techniques in modern LLM application development: by grounding model outputs in verified external knowledge, it reduces hallucination and lets an LLM operate on up-to-date, domain-specific information the base model was never trained on. A few principles carry forward across all of the patterns in this chapter:

  • Chunking strategy matters. How a document is split directly determines what can be retrieved; tune it before tuning the LLM.

  • Retrieval quality gates generation quality. No LLM can produce a faithful answer from irrelevant retrieved chunks — evaluate retrieval separately from generation.

  • MMR over pure similarity for broad queries. Diversity in the retrieved set matters when a query spans multiple sub-topics.

  • Evaluate faithfulness, not just fluency. A confident-sounding answer can still be ungrounded; measure groundedness explicitly.

  • RAG and agents are complementary. RAG grounds factual recall; agentic control handles multi-step reasoning about when and what to retrieve.

7.7.6. Exercises and discussion#

  1. Hybrid vs. dense-only retrieval Construct a query containing a rare technical term or code that appears verbatim in only one chunk. Compare results from dense-only retrieval and the hybrid ensemble above. Does BM25’s exact-match behavior recover a chunk that dense retrieval missed?

  2. Router failure modes The keyword-based router above will misroute any query that doesn’t contain its trigger keyword. Design three test queries that expose this failure, then propose a routing approach that would handle them correctly.

  3. When is agentic RAG worth the cost? Describe a question that requires two sequential retrieval calls to answer correctly (the second query depends on the answer to the first). Explain why a fixed single-pass RAG chain would fail on this question and how an agentic loop resolves it.
