7.4. Retrieval-Augmented Generation: Foundations and Document Ingestion#

7.4.1. Learning objectives#

By the end of this section, you should be able to:

  • Explain why grounding LLM outputs in external knowledge reduces hallucination compared to relying on parametric memory alone.

  • Describe the three stages of a RAG pipeline and what each stage is responsible for.

  • Explain the role of chunking and select reasonable chunk_size and chunk_overlap values for a given document type.

  • Compare local and API-based embedding models and justify a choice for a given deployment constraint.

  • Compare ChromaDB and FAISS as vector store backends and identify which suits a given use case.

7.4.2. Why Ground LLM Outputs in External Knowledge?#

A language model’s knowledge is frozen at training time and compressed into its parameters. When asked about information that postdates training, is domain-specific, or is simply rare in the training distribution, the model tends to hallucinate — producing fluent, confident text that is not factually grounded.

Retrieval-Augmented Generation (RAG) [Lewis et al., 2020] addresses this by retrieving relevant passages from an external knowledge source at inference time and injecting them into the prompt, so the model generates conditioned on verified context rather than on memory alone.

7.4.3. The Three Stages of a RAG Pipeline#

Table 7.7 Three Stages of a RAG Pipeline#

Stage

What Happens

Ingestion

Documents are loaded, chunked, embedded, and stored in a vector store

Retrieval

A user query is embedded and matched against stored chunks

Generation

Retrieved chunks are injected into the prompt and the LLM generates a grounded answer

This section covers ingestion. Retrieval and generation are covered in the sections that follow.

7.4.4. Chunking Documents#

LLMs have a bounded context window, so an entire document cannot simply be pasted into a prompt. Chunking splits a document into smaller, overlapping pieces so that only the most relevant pieces are retrieved and injected at query time.

Table 7.8 Text Chunking Parameters#

Parameter

Effect

chunk_size

Maximum characters per chunk

chunk_overlap

Characters shared between adjacent chunks, preserving context across a chunk boundary

Small chunks improve retrieval precision (less irrelevant text per chunk) but can fragment ideas that span multiple sentences; large chunks preserve context but dilute relevance and increase the amount of text injected per retrieved chunk. chunk_overlap mitigates fragmentation by letting adjacent chunks share a short window of text.

from langchain_text_splitters import RecursiveCharacterTextSplitter

# Plain Text Example
sample_text = """
LangChain is a framework for developing applications powered by language models.
It provides tools for chaining prompts, managing memory, and integrating external tools.
RAG stands for Retrieval-Augmented Generation. It grounds LLM outputs in external knowledge.
ChromaDB is a vector store optimized for storing and retrieving embeddings efficiently.
FAISS is a library developed by Meta for efficient similarity search at scale.
Embeddings are numerical representations of text that capture semantic meaning.
"""

splitter = RecursiveCharacterTextSplitter(
    chunk_size=200,
    chunk_overlap=20
)

text_chunks = splitter.create_documents([sample_text])

print(f" Split into {len(text_chunks)} chunks\n")
for i, chunk in enumerate(text_chunks):
    print(f"Chunk {i+1}: {chunk.page_content}\n")

 Split into 3 chunks

Chunk 1: LangChain is a framework for developing applications powered by language models.
It provides tools for chaining prompts, managing memory, and integrating external tools.

Chunk 2: RAG stands for Retrieval-Augmented Generation. It grounds LLM outputs in external knowledge.
ChromaDB is a vector store optimized for storing and retrieving embeddings efficiently.

Chunk 3: FAISS is a library developed by Meta for efficient similarity search at scale.
Embeddings are numerical representations of text that capture semantic meaning.

RecursiveCharacterTextSplitter tries to split on natural boundaries first (paragraphs, then sentences, then words) before falling back to a hard character cut, which tends to produce more semantically coherent chunks than a naive fixed-width split.

7.4.5. Embedding Strategies#

Embeddings convert text chunks into numerical vectors that capture semantic meaning. Retrieval quality is bounded by embedding quality: two chunks that are semantically related should map to nearby vectors.

from langchain_community.vectorstores import Chroma
from langchain_community.vectorstores import FAISS

# Build ChromaDB vector store from text chunks
chroma_db = Chroma.from_documents(
    documents=text_chunks,
    embedding=embeddings,
    persist_directory="./chroma_db"
)

# Build FAISS vector store from the same text chunks
faiss_db = FAISS.from_documents(
    documents=text_chunks,
    embedding=embeddings
)

Both stores expose the same similarity_search interface, so switching backends does not require changing retrieval or generation code — only the constructor call. This is why the retriever abstraction (covered next) is a useful seam in the pipeline.

7.4.7. Exercises and discussion#

  1. Chunk size sensitivity Take a multi-page document and index it with three different chunk_size values (e.g. 100, 300, 800 characters, holding chunk_overlap proportional). For a fixed set of test queries, compare the retrieved chunks qualitatively. At what chunk size does retrieval start returning chunks that mix unrelated ideas?

  2. Embedding model trade-offs Embed the same set of chunks with a local sentence-transformers model and, if available, an API-based embedding model. Compare retrieval results on the same queries. Under what deployment constraints (cost, latency, privacy) would you choose one over the other?

  3. Vector store selection Given a corpus of one million documents that must be queried with sub-100ms latency and does not need to persist across restarts, would you choose ChromaDB or FAISS? Justify your answer using the comparison table above.
